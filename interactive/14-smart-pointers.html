shared_ptr and weak_ptr

Shared ownership: shared_ptr and the control block, reference cycles and weak_ptr, and the pitfalls. Assumes unique_ptr, which covers ownership and the rule that a smart pointer is only for objects you own.

shared_ptr and the control block

  • A shared_ptr is two pointers: to the object and to a control block holding the strong count, the weak count and the deleter.
  • make_shared allocates object and control block together (one allocation). shared_ptr<T>(new T) allocates twice.
  • The deleter is not part of the shared_ptr type (unlike unique_ptr): type-erased in the control block.
  • The counts are atomic: copying or destroying shared_ptrs on several threads is safe. The object is not protected, and changing the same shared_ptr variable from two threads is a race.
  • Copying costs an atomic increment. On hot paths pass const shared_ptr& or the object itself, not a copy per call.

Reference cycles and weak_ptr

If A holds a shared_ptr<B> and B holds a shared_ptr<A>, each keeps the other alive: neither is ever destroyed. Compiled: after the scope, both objects were still alive (leaked). Make the back link (child to parent) a weak_ptr: both were destroyed.

  • lock() is the only way to use the object: it gives a shared_ptr that keeps it alive while you work, or null.
  • Typical uses: parent links, caches, observer lists that must not keep subscribers alive.
  • A weak_ptr keeps the control block alive (not the object) until the last weak reference goes.

Pitfalls and enable_shared_from_this

One control block per object Never build a second shared_ptr from a raw pointer or from this. Copy an existing one.

When a member function needs a shared_ptr to its own object (to register itself, to hand to a callback), inherit std::enable_shared_from_this and call shared_from_this():

Cheat sheet

Answer aloud, then open.

unique_ptr vs shared_ptr vs weak_ptr?

unique_ptr: sole owner, move-only, zero overhead. shared_ptr: reference-counted shared ownership with a control block and atomic count. weak_ptr: non-owning observer used to break cycles and to check whether a shared object is still alive (lock()).

Is shared_ptr thread-safe?

The reference count is atomic, so copying and destroying shared_ptrs from different threads is safe. The pointed-to object is not protected: concurrent access to it still needs synchronization. Concurrently modifying the same shared_ptr variable is also a race.

Why prefer make_unique / make_shared?

No naked new, less typing (and exception safe before C++17), and make_shared allocates the object and its control block once instead of twice.

How do you break a shared_ptr cycle?

Make one direction (usually the child's link to its parent) a weak_ptr. It does not count toward ownership, so the objects can be destroyed; use lock() to get a temporary shared_ptr when needed.

How do you pass a smart pointer to a function?

If the function only uses the object, pass a reference or raw pointer, not the smart pointer. To transfer ownership, take a unique_ptr by value and have the caller std::move. To share, take a shared_ptr by value. Return unique_ptr from factories.

Why can two shared_ptrs built from the same raw pointer crash?

Each creates its own control block and count, so the object is deleted twice. Copy an existing shared_ptr, or inherit enable_shared_from_this when an object must hand out a shared pointer to itself.

Does unique_ptr cost anything compared with a raw pointer?

Not with the default deleter: it is the same size and the destructor inlines to a delete. A stateful deleter (a capturing lambda, a function pointer) makes it larger.
