Casts and Type Conversions

What the compiler converts for you and where it loses information, why the C-style cast is a trap, and the named casts: static_cast, dynamic_cast, const_cast, reinterpret_cast and bit_cast. Assumes Types, Initialization and Constants.

What the compiler converts for you

You do not have to write a cast for most conversions: the compiler converts between arithmetic types by itself. These implicit conversions follow fixed rules, and the surprises come from not knowing them.

Compiled results of the classic surprises:

ExpressionResultWhy
-1 < 1ufalsethe signed value is converted to unsigned and becomes huge
uint8_t(200) + uint8_t(100)300, stored back as 44small types are promoted to int before arithmetic; storing back wraps
7 / 23integer division; 7 / 2.0 is 3.5
int g = 3.7;3conversion to an integer truncates toward zero (-3.9 becomes -3)
char 0xFF widened to int-1 (signed char)whether plain char is signed is implementation-defined
  • Never compare signed with unsigned (-Wsign-compare); use std::ssize or cast deliberately.
  • Single-argument constructors are implicit conversions too: mark them explicit (see explicit and conversion operators).

Narrowing and braces

A conversion that can lose information is called narrowing: double to int, a wide integer to a narrower one, a value that does not fit. With = it compiles quietly. With braces the language requires the compiler to complain, so braces are a free safety check.

Conversion in bracesAllowed?
a constant that fits the target (unsigned char c{200})yes
a constant that does not fit (unsigned char c{300})no: compile error
floating point to integer (int b{3.0})no: even when the value would fit
a wider integer variable to a narrower onemust be diagnosed; some compilers only warn, so turn warnings on
integer to double where every value fitsyes
HabitInitialize with braces. When you really want the loss, say so with a cast (next sections), so the next reader knows it is intentional.

The C-style cast and why to avoid it

C has one cast, (T)x. In C++ it is a trap: it tries the C++ casts in a fixed order and uses the first one that compiles, so a small mistake silently becomes a dangerous conversion.

C++ replaces it with four named casts. Each states its intent, and you can search for it (grep static_cast). A C-style cast never turns into dynamic_cast.

CastUse forDanger
static_cast<T>(x)well-defined conversions you can see are finelow
dynamic_cast<T>(x)a checked downcast in a class hierarchyruntime cost
const_cast<T>(x)add or remove constwriting to a truly const object is undefined
reinterpret_cast<T>(x)reinterpret raw bitsvery high, rarely correct

static_cast: the everyday cast

static_cast does the conversions the compiler already knows how to do, but explicitly. It is checked at compile time and refuses nonsense such as int to pointer.

UseExample
number to numberstatic_cast<double>(i), static_cast<int>(x)

derived to base, base to derivedthe base-to-derived direction is unchecked

dynamic_cast: checked downcasts

dynamic_cast asks the object what it really is at run time. If the answer is not the type you asked for, the cast fails safely instead of lying.

  • A pointer cast returns nullptr on failure; a reference cast throws std::bad_cast. Compiled: the Derived object passed, the Other object gave null and, as a reference, bad_cast.
  • It needs a polymorphic base: at least one virtual function. That is how the object carries its real type (see the vtable).
  • It costs a lookup at run time. typeid(*p) == typeid(Derived) asks for an exact match instead.
  • A chain of if (dynamic_cast<A*>...) else if (dynamic_cast<B*>...) usually means a virtual function is missing.

const_cast, reinterpret_cast and bit_cast

const_cast: only for old APIs

It removes const from the type, not from the object. Writing through the result is only defined if the object was not const to begin with; writing to a truly const object (a string literal, a const int) is undefined behavior.

reinterpret_cast: look at the bytes

Cheat sheet

Answer aloud, then open.

When would you use dynamic_cast?

For a checked downcast from a polymorphic base to a derived type when you cannot express the need through a virtual function. It returns null (pointers) or throws bad_cast (references) on failure. Frequent use suggests a design problem.

The four named casts?

static_cast for well-defined conversions, dynamic_cast for checked downcasts, const_cast to add or remove const (modifying a truly const object is UB), reinterpret_cast to reinterpret bits (rarely correct). Never a C cast: it can silently pick any of them.

What is wrong with if (-1 < 1u)?

The signed operand is converted to unsigned, becoming a huge value, so the comparison is false. Avoid mixing signed and unsigned; compile with -Wsign-compare.

What does a C-style cast (T)x do?

It tries static_cast, then static_cast plus const_cast, then reinterpret_cast, and uses the first that compiles. It can silently remove const or reinterpret bytes, and it never becomes dynamic_cast. Use the named casts so the intent is visible and searchable.

What is narrowing, and how do braces help?

A conversion that can lose information, such as double to int or a value that does not fit. With = it compiles silently; with braces the compiler must diagnose it, for example int b{3.7} is an error.

How do you reinterpret the bits of a float as an integer safely?

With std::memcpy or std::bit_cast (C++20). A reinterpret_cast of the pointer and a read through it as another type violates the aliasing rules.
