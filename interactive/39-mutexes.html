Protecting a class

Good locking
  • Keep critical sections short; do slow work (I/O, computation) outside.
  • Mutex next to its data; never hand out references to that data.
  • Never call unknown code (callbacks, virtuals) while locked.
  • Too much locking means contention: the program becomes serial.

How long to hold a lock

A mutex serializes the code under it, so every extra line under the lock is time other threads spend waiting. The pattern is: do the slow parts first or after, and keep the lock for the shared access only.

Do under the lockDo not do under the lock
read or write the shared dataI/O, printing, sleeping
restore the invariant before unlockingcalling unknown code or callbacks
copy out what you needwaiting for another lock or a future

recursive_mutex is a design smell

It works (compiled: balance 10), but it hides a design problem: depositTwice does not know what state deposit assumes. Prefer a public method that locks once and a private depositLocked() that assumes the lock is held. A plain std::mutex locked twice by one thread is undefined behaviour (usually a deadlock).

Reader-writer lock

  • A shared_mutex costs more than a mutex per lock. It pays off only when there are many readers and each read holds the lock for a while.
  • Writers can starve if readers never leave (implementation-defined fairness).
  • try_lock() returns immediately with true or false: compiled, a second thread's try_lock on a held mutex returned false; try_lock_for(20 ms) on one held for 200 ms returned false after 20 ms.

std::call_once

Use it (or a function-local static) for lazy initialization shared by several threads, instead of a hand-written double-checked lock.

Key point"When would you use a recursive mutex?" Rarely, and say so: it usually means a method that locks calls another that also locks. Restructure into a locking public method and a lock-assuming private one.

Fix: offer whole operations

Why does std::stack split top() and pop()? If pop() returned by value and the copy threw after removal, the element would be lost. A concurrent version must merge them: out-parameter, std::optional, shared_ptr<T>, or a non-throwing move.

Same pattern elsewhere:

Racy sequenceWhole-operation fix
if (!m.contains(k)) m[k] = v;one insert/try_emplace call that does both under the lock
if (q.size() < max) q.push(x);a try_push that checks and pushes under one lock
if (!file_exists(p)) create(p);an atomic "create if absent" call (for example the OS O_EXCL flag)
if (counter.load() > 0) counter--;a compare_exchange loop
Key point"Mutex in every method, so thread-safe?" No: each call is safe, the caller's sequence is not. Provide combined operations like try_pop and protect the whole invariant.

Cheat sheet

Answer aloud, then open.

lock_guard vs unique_lock vs scoped_lock?

lock_guard: simplest RAII lock for a scope. unique_lock: flexible (unlock/relock, deferred, movable) and needed by condition variables. scoped_lock (C++17): locks multiple mutexes at once with deadlock avoidance.

My class locks a mutex in every method. Is it thread-safe?

Not necessarily. Each call is safe on its own, but a caller's sequence of calls is not atomic. The classic case is a shared stack: if (!s.empty()) { v = s.top(); s.pop(); } races, because another thread can pop between the check and the use. The cause is the interface (it is also true of a lock-free stack), so the fix is to provide whole operations such as std::optional<T> try_pop() that check and remove under one lock.

What does std::scoped_lock do?

It locks several mutexes in one step with a deadlock-avoidance algorithm and unlocks them in its destructor. Use it whenever you need more than one lock.

When would you use std::shared_mutex?

For read-mostly data: many readers take a shared_lock at the same time, a writer takes a unique_lock and excludes everyone. It only pays when reads greatly outnumber writes.
