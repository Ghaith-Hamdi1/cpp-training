The C++ Standard Template Library

Containers hold data, algorithms work on it, and iterators connect the two. Knowing which container to pick, what each operation costs and when iterators break is a staple of C++ interviews.

The big picture

The STL has three cooperating parts:

PartWhat it isExamples
Containersclasses that own and organise a collection of elementsvector, map, set, deque
Iteratorsgeneralised pointers that walk a containerv.begin(), m.find(k)
Algorithmsgeneric functions that operate on iterator rangessort, find, accumulate

Algorithms never touch containers directly. They only see a pair of iterators [first, last), so one std::sort works on a vector, an array or a deque, and one container can be used with hundreds of algorithms. That separation is the design genius of the library.

Default choiceIf you do not have a reason to pick something else, use std::vector. Contiguous memory is so cache-friendly that it often beats "theoretically better" containers for realistic sizes.

vector: the workhorse

A vector stores its elements in one contiguous heap array. It tracks two numbers: size (elements in use) and capacity (slots allocated). When push_back finds no spare capacity it allocates a bigger buffer, moves or copies every element across, and frees the old one. That is O(n) once in a while, but because capacity grows geometrically the average cost per push_back is amortised O(1).

reserve vs resizereserve(n) only allocates space (capacity). resize(n) changes the number of elements (size). Calling v[5] = x after only reserve(10) is undefined behavior: element 5 does not exist yet.

Container adaptors

They wrap another container and restrict the interface: std::stack (LIFO: push/pop/top), std::queue (FIFO: push/pop/front) and std::priority_queue (a heap: top() is the largest element by default).

Which container should I use?

Pick what you mostly do. The advisor gives the container and the reason.

Interview angle"vector vs list?" Answer with memory, not just big-O: a vector is contiguous, so traversals are cache-friendly and in practice beat a list even for inserts in the middle at modest sizes. A list wins only when you need stable iterators/references and cheap splicing.

Iterators

An iterator behaves like a pointer: *it reads the element, ++it moves on, it == end ends the walk. Every container exposes begin() (first element) and end() (one past the last). Ranges are half-open: [begin, end).

This is why std::sort needs random-access iterators and does not work on std::list (which has its own member list.sort()).

Algorithms

The <algorithm> and <numeric> headers hold over a hundred generic functions. Prefer them to hand-written loops: they are named (so they document intent), tested, and often faster. Most take a predicate or comparator, usually a lambda.

Algorithms only see iterators, so they cannot change a container's size. std::remove shifts the kept elements forward and returns the new logical end, leaving junk after it. To really remove, use the erase-remove idiom:

Comparators must be a strict weak orderingUse <, never <=. A comparator that returns true for equal elements violates the contract and can crash std::sort or corrupt a std::set. std::sort is O(n log n) and not stable; use std::stable_sort to preserve the order of equal elements.

Strings and string_view

  • std::string stores small strings (about 15 chars with common implementations) inline without a heap allocation: the small string optimisation.
  • string_view must never outlive the string it points into. Returning a string_view to a local string, or storing one from a temporary, dangles.
  • Use std::stringstream / std::getline for parsing and formatting streams.

Interview cheat sheet

How does std::vector grow?

When size == capacity it allocates a larger buffer (geometric growth, typically 1.5x to 2x, implementation-defined), moves or copies the elements, and frees the old buffer. This makes push_back amortised O(1), but it invalidates all iterators, pointers and references. reserve avoids the reallocations.

map vs unordered_map?

map: balanced tree, sorted iteration, O(log n), needs operator<, supports range queries. unordered_map: hash table, average O(1) (worst O(n) with many collisions), no order, needs a hash and ==. Choose unordered_map for plain lookups and map when you need order.

push_back vs emplace_back?

push_back takes an existing object (a copy or move). emplace_back forwards its arguments to the element's constructor and builds it in place, avoiding a temporary. For simple types there is no difference; for objects with expensive construction emplace_back can save a move.

What is the erase-remove idiom?

std::remove/remove_if only moves the elements to keep to the front and returns the new end; it cannot shrink the container. Pass that to the container's erase to actually delete the tail: v.erase(std::remove_if(...), v.end()). C++20 has std::erase_if.

What is a hash collision and how is it handled?

Two different keys hash to the same bucket. The standard library's unordered containers resolve it with chaining (a bucket holds a list of entries), so lookups in a heavily colliding bucket degrade toward O(n). A good hash function and a sensible load factor (rehash, reserve) keep it near O(1).

Why can't I std::sort a std::list?

sort needs random-access iterators (it jumps around by index). A list only provides bidirectional iterators, so it has its own member function list::sort.

Which container for a task queue? For "top K" elements?

A queue (std::queue, backed by deque) for FIFO tasks. A priority_queue (heap) for top K: keep a heap of size K and compare against its root: O(n log K).
