RAII: the central idea

RAII: tie a resource (memory, file, lock, socket) to an object. Acquire in the constructor, release in the destructor. Destructors run even when an exception is thrown, so nothing leaks.

Watch a throw in the middle:

vector, unique_ptr, lock_guard, fstream are all RAII. Never manage a resource with a bare new/delete, lock()/unlock() or fopen/fclose: wrap it.

Key pointRAII binds resource lifetime to object lifetime: automatic, exception-safe cleanup. It replaces try/finally and removes the need for a garbage collector.

Exceptions and stack unwinding

  • Throw by value, catch by const& (catching by value slices a derived exception).
  • Stack unwinding: leaving scopes runs destructors, in reverse order of construction, until a catch matches. This is why RAII is exception-safe.
  • A destructor must never throw: if it throws while another exception is unwinding, std::terminate is called. Destructors are implicitly noexcept.
  • A constructor that throws leaves no object: the destructors of already-built members and bases run, its own does not.
  • catch (...) catches everything; rethrow with a bare throw; (never throw e;, which copies and slices).
  • Derive your own exceptions from std::exception (or a standard subclass) so generic handlers still work.
CostThe no-throw path is almost free, but a throw is orders of magnitude slower than a return and its latency is unpredictable. Do not throw on a hot path or as ordinary control flow (see Exceptions, error codes and optional).

RAII everywhere: guards and standard wrappers

Almost every resource has a standard RAII wrapper. Use it instead of a manual acquire/release pair.

  • A RAII class owns one resource. Copying it must be deleted (one owner) or a deep copy; moving transfers ownership (the Rule of Five, OOP lesson; Move Semantics).
  • Prefer the Rule of Zero: hold resources in members that are already RAII, and you write no destructor at all.

Getting the strong guarantee: build aside, then swap

Do everything that can fail on a copy, then publish the result with an operation that cannot throw. If anything throws before the swap, the object is unchanged.

noexcept

  • noexcept promises a function will not throw. If it does anyway, the program calls std::terminate: there is no unwinding past it.
  • Destructors are noexcept by default. A throwing destructor during unwinding means two exceptions at once, and the program terminates.
  • Mark move operations and swap noexcept when they cannot throw. std::vector grows by moving its elements only if the move constructor is noexcept; otherwise it copies, to keep the strong guarantee. Compiled example: growing a vector whose elements have a noexcept move made 0 copies; with a possibly-throwing move it copied every element.
  • noexcept(expr) asks the compiler whether an expression can throw; generic code uses it to pick the cheap path (std::move_if_noexcept).
  • Do not mark a function noexcept just to be fast: a wrong promise turns an error into a crash.

Exceptions, error codes and optional

SituationUse
a failure the caller cannot sensibly handle here (out of memory, broken invariant, constructor failure)exception: it unwinds to code that can cope
an expected failure in normal flow (bad input, "not found", parse error)return a value that says so: std::optional, an error code or enum, std::expected (C++23)
a hot path with steady latency (real-time code)no exceptions: error codes or optional (Low-Latency C++)
a noexcept context, or a destructornever throw: catch inside and log or ignore
  • Exceptions keep the normal path clean and cannot be silently ignored; the cost is that a throw is slow and the control flow is invisible.
  • Return values make failure explicit and cheap; the cost is that every caller must check, and [[nodiscard]] helps remind them.
  • Constructors cannot return a code: either throw, or use a factory function returning optional or an expected.
  • Be consistent inside a module, and document what a function can throw.
Key point"Exceptions or error codes?" Exceptions for rare failures that need unwinding, return values for expected failures and for hot paths. Mention RAII (so nothing leaks either way) and that a destructor must never throw.

Cheat sheet

Answer aloud, then open.

What is RAII and why is it important?

It binds a resource's lifetime to an object: acquire in the constructor, release in the destructor. Cleanup is automatic and exception-safe because destructors run on every exit path. It replaces try/finally and is why C++ needs no garbage collector.

What is stack unwinding?

When an exception propagates, the runtime exits scopes up the call stack, calling the destructors of all fully constructed locals until a handler is found. It is what makes RAII exception-safe.

Why should destructors not throw?

Destructors run during unwinding. If one throws while another exception is active, std::terminate is called. Destructors are noexcept by default; catch and handle errors inside them.

What are the exception-safety guarantees?

No-throw (never throws: destructors, swap, moves), strong (if it throws, the state is exactly as before: commit or rollback), and basic (nothing leaks and invariants hold, but values may have changed). Get the strong guarantee by doing the work on a copy and publishing with a non-throwing swap.

Why mark move operations noexcept?

std::vector moves its elements when it grows only if the move cannot throw; otherwise it copies them to keep the strong guarantee. A missing noexcept silently turns every reallocation into a round of copies.

What happens if a noexcept function throws?

std::terminate is called: the exception does not propagate. So only promise noexcept when it is true.

Exceptions or error codes?

Exceptions for rare failures the local code cannot handle (and constructors); return values (optional, error codes, expected) for expected failures and for hot paths where a throw's cost and unpredictability are unacceptable.

How do you run cleanup on every path without finally?

Put it in a destructor: a standard RAII wrapper (lock_guard, unique_ptr, fstream) or a small scope guard class. Release the guard on success to commit.
