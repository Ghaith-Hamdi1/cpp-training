Deadlock

A deadlock: threads wait for each other forever. A holds a wants b; B holds b wants a. Step A once, B once, then try to go on:

"Run 500 random schedules": many end in deadlock. In real programs it may occur once in a million runs, only in production.

It needs all four (Coffman conditions); remove one and it cannot happen:

  1. Mutual exclusion: one holder at a time
  2. Hold and wait: holds one lock, waits for another
  3. No preemption: a lock cannot be taken away
  4. Circular wait: A waits for B, B for A

Four guidelines, one idea

Do not wait for a thread that might be waiting for you.

  1. Avoid nested locks. If you need several, take them in one step with std::scoped_lock.
  2. No user-supplied code under a lock. A callback may take another lock, or keep a pointer to your data: Never pass out a pointer or reference to protected data.
  3. Fixed lock order. Hand-over-hand locking on list nodes deadlocks when two threads walk in opposite directions. Fix the traversal direction.
  4. Lock hierarchy. Each mutex has a level; a thread may only lock a lower level than it holds. Violations throw the first time, even if the unlucky timing never occurs. It is a small wrapper around std::mutex that records the current level in a thread_local variable and throws if you lock upward. The idea is worth knowing; in practice, std::scoped_lock and a documented lock order cover most programs.
No mutex neededTwo threads that join() each other deadlock, as does any cycle of futures or condition-variable waits.
Key point"Prevent deadlock?" Global lock order; std::scoped_lock; no foreign code under a lock; short locks; no nesting; try_lock with back-off. Re-locking a non-recursive mutex you own is undefined behavior.

Livelock, starvation and lost wakeups

Deadlock is the loudest bug but not the only way threads fail to make progress.

ProblemWhat happensCPUTypical cause

  • Livelock is cured by randomizing the retry delay or by giving the threads a fixed order.
  • std::mutex::try_lock never blocks: use it to back off instead of waiting, but then handle failure.

Finding a deadlock

A deadlock rarely announces itself: the program just stops. Finding it is a matter of asking every thread where it is.

ToolWhat it shows
gdb: thread apply all btthe stack of every thread: look for several threads inside lock, wait or join
ThreadSanitizer (-fsanitize=thread)lock-order inversions (a before b in one place, b before a in another), even if no hang occurred
a lock hierarchy in debug buildsthrows the first time a thread locks against the order

Reproduce itAdd a short sleep_for between the two lock calls while debugging: it widens the window so the deadlock happens every time instead of once a month.

Cheat sheet

Answer aloud, then open.

What is a deadlock and how do you prevent it?

Threads wait for each other's locks forever. Needs mutual exclusion, hold-and-wait, no preemption and circular wait. Prevent with a consistent global lock order, std::scoped_lock/std::lock for multiple mutexes, short critical sections, no calls to foreign code under a lock, or try_lock.

Can threads deadlock without any mutex? What are the practical rules against deadlock?

Yes: two threads that join() each other, or any cycle of waits on futures or condition variables. The rules all mean "do not wait for a thread that might be waiting for you": avoid nested locks (or take several with scoped_lock), never call user-supplied code or leak references to protected data while holding a lock, lock in a fixed order, and use a lock hierarchy so a wrong order is caught immediately at runtime.

What are the four Coffman conditions?

Mutual exclusion, hold and wait, no preemption and circular wait. All four must hold for a deadlock; breaking any one prevents it. A global lock order breaks circular wait.

Why is std::scoped_lock(a, b) safe when two threads pass the mutexes in opposite orders?

It takes the locks with a deadlock-avoidance algorithm (try-and-back-off or ordering), so the order of the arguments does not matter.
