Copy versus Move, and std::move

What copying costs, what std::move really does (a cast, not a move), what a moved-from object is, and when a move silently becomes a copy. Assumes Lvalues and Rvalues.

What a copy costs

Copying a vector of a million ints allocates a new buffer and copies a million values. If the source is a temporary that is about to die anyway, that work is wasted. A move instead steals the inside: it copies the pointer and size, and leaves the source empty.

CopyMove
allocates memoryyesno
copies elementsall of them, O(n)none, O(1)
source afterwardsunchangedvalid but unspecified (usually empty)
used when the source isan lvalue you still needan rvalue, or std::move(x)

Not every type benefits. A move of an int or a small struct is just a copy; the gain is for types that own a resource: vectors, strings, unique_ptr, file handles.

What std::move really does

The name is misleading: std::move(x) moves nothing. It is a cast, equal to static_cast<T&&>(x), that changes the expression from an lvalue to an rvalue. The move constructor or move assignment chosen afterwards does the stealing.

Key point"What does std::move do?" Nothing at run time: an unconditional cast to an rvalue reference. Whether anything is stolen depends on the type having a move operation.

Moved-from objects

After auto t = std::move(s); the object s still exists and its destructor will still run. The standard promises only that it is in a valid but unspecified state.

You mayYou may not rely on
destroy itits old value
assign a new value to itits size or contents
call functions with no preconditions: clear(), empty(), size()reading elements
  • For standard types, a moved-from object is usually empty, but only your own types can promise more.
  • Move only at the last use. After auto b = std::move(a); treat a as empty.
  • Moving inside a loop is a bug: the second iteration sees a moved-from object.

When std::move copies anyway

Two situations make std::move quietly do nothing useful.

SilentNone of these is an error. The code is correct and slower than you think. Never return const values by value either: it disables the move at the caller.

Which standard types are cheap to move

A move is only cheap when there is a pointer to hand over. Knowing which standard types have one helps you predict the cost.

TypeMove costWhy
std::vector, std::map, std::listO(1)the elements live on the heap: only the pointers change hands
std::stringO(1) for long text, a copy for short textshort strings are stored inside the object (small string optimization)
std::unique_ptrO(1), and the only way to transfer itcopy is deleted; a move copies one pointer and nulls the source
std::array<T, N>O(N)the elements are stored inline, so each one is moved (compiled: 3 moves for N = 3)
int, double, plain structssame as a copynothing to steal

Containers of movable elements use moves internally: push_back of a temporary, growth, std::sort swapping elements and std::erase shifting them. That is why moves matter even when you never write std::move.

Cheat sheet

Answer aloud, then open.

What does std::move actually do?

Nothing at runtime: it is an unconditional cast to an rvalue reference. It enables the move constructor or move assignment to be chosen. The moved-from object stays valid but unspecified. On a const object it silently copies, because a const rvalue cannot bind to a move constructor.

What state is a moved-from object in?

Valid but unspecified: you may destroy it or assign a new value to it, but not rely on its contents. For standard types it is usually empty.

Why does std::move on a const object copy?

The cast gives a const T&&, which cannot bind to the move constructor's T&& parameter, so overload resolution picks the copy constructor. No error, just a copy.

When is moving not faster than copying?

For types that own no resource: an int or a small struct is just copied. The gain is for types that own memory, handles or other resources.

Is it safe to use an object after std::move?

Only to destroy it or assign a new value to it. Its contents are unspecified, so do not read them.
