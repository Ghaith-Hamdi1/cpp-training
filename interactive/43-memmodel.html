The Memory Model: Orders and Happens-Before

Why one thread can see another's writes late or out of order, release and acquire, the five memory orders, happens-before, the ordering patterns that matter, and thread-safe data structures. Assumes Atomics and Compare-and-Swap.

Why the order matters

The operations in your source are not executed, or observed, in source order across threads. The compiler reorders instructions, and each core has a store buffer and caches, so a write by one thread reaches another thread later, or even after a write that came after it.

Who reordersWhy
the compilerto keep values in registers and to schedule instructions
the CPUout-of-order execution and store buffers
the cache systemeach core sees memory updates at a different time

Atomics let you say how much ordering you need between this operation and the others.

Release and acquire: the one rule to learn

  • A release store publishes: every write the thread made before it becomes visible to any thread that reads the stored value with an acquire load.
  • The release/acquire pair synchronizes-with, and that creates a happens-before edge: data = 42 happens before the consumer's read, so the read is not a data race and sees 42.
  • happens-before is the formal "must be visible" relation. Within one thread it is program order; across threads it comes only from synchronization (atomics, mutexes, join, futures).

Try it. Flush the producer's writes to memory in different orders and see what the consumer prints:

  • Both sides must take part: a release store read by a relaxed load publishes nothing.
  • A fence (std::atomic_thread_fence) gives the ordering without tying it to one variable. Know it exists; reach for acquire/release on the atomic first.
  • Without any synchronization, two threads touching the same non-atomic variable (one writing) is a data race: undefined behaviour, not merely "stale data".

The five memory orders

There are five orders. Atomic operations take one as an optional argument; the default is the strongest.

OrderGuaranteeUse
relaxedonly atomicity (and a single total order for that variable)counters and statistics nobody synchronizes on

release (stores)nothing before it moves after it; publishes earlier writessetting that flag or pointer

Happens-before

Happens-before is the formal rule that decides what a thread must see. Inside one thread it is just program order. Between threads it exists only because of synchronization: a release/acquire pair, a mutex unlock followed by a lock, thread start and join, a future becoming ready.

SynchronizationCreates happens-before between
release store, acquire load of the same atomiceverything before the store and everything after the load
mutex.unlock(), then lock() by another threadthe critical sections
std::thread constructorthe code before it and the start of the thread function
join()the end of the thread and the code after the join
promise.set_value(), future.get()the value and its reader

Be honest about what you knowStart with a mutex or seq_cst, measure, and weaken orders only when you can say which happens-before edge each one provides. "I use acquire/release for publication, relaxed for counters" is a sound rule of thumb.

Double-checked locking: the classic trap

Double-checked locking is the classic place where a wrong order breaks a program: the pointer can be seen before the object it points to is fully built.

Without the release/acquire pair, another thread could see the pointer before the constructor's writes. In practice use a function-local static or std::call_once and let the compiler do this.

Thread-safe data structures

Three levels, in the order you should try them:

LevelHowExample
1. One coarse locka mutex around the whole structurea stack or map with a mutex (see the interface races in Multithreading)
2. Fine-grained locksdifferent mutexes for different parts, so threads that touch different parts do not waita queue with a head mutex and a tail mutex; a hash table with one mutex per bucket
3. Lock-freeatomics and CAS loops, no mutexa Treiber stack, an SPSC ring buffer

Read-mostly: a lookup table

A price table read by many threads and updated rarely: std::shared_mutex with shared_lock for readers and unique_lock for writers (Other mutex types). Return copies or small values, never references into the table.

Lock-free is not faster by defaultA contended CAS loop can be slower than a mutex, and a bug shows up once a month on a customer machine. Use a mutex first, measure, and use a proven library (or the SPSC ring when one producer and one consumer is enough) before writing your own.
  • Wait-free (every thread finishes in a bounded number of steps) is stronger than lock-free (some thread always makes progress) which is stronger than obstruction-free.
  • Design the interface first: whole operations (tryPop returning an optional), not empty() then pop().

Cheat sheet

Answer aloud, then open.

What are the memory orders?

seq_cst (default, strongest, one global order), acquire/release (pair a release store with an acquire load to publish data), acq_rel for read-modify-write, and relaxed (atomicity only). Start with the default; weaken only with a reason and a clear happens-before argument.

What does release/acquire guarantee?

Everything the producer wrote before a release store is visible to a thread that reads the stored value with an acquire load. The pair synchronizes-with, which gives a happens-before edge, so the earlier plain writes are not a data race.

What does happens-before mean?

If A happens-before B, then A's effects are visible to B. Within a thread it is program order; between threads it exists only through synchronization: atomics with matching orders, mutex unlock/lock, thread start and join, futures. Two conflicting accesses without a happens-before relation are a data race.

When is relaxed enough?

When no other data depends on the atomic: a statistics counter, an id generator, a shutdown flag that carries no data. The final value is correct, but it orders nothing else.

Why can code with a wrong memory order work on x86 and fail on ARM?

x86's hardware already orders ordinary loads and stores like release/acquire, so missing orderings are hidden. ARM and POWER reorder far more, so the same code can read stale data there. The C++ model, not the PC you tested on, defines correctness.

How is a reference count made thread-safe, and with which orders?

With an atomic counter: increments can be relaxed, the decrement is acq_rel so the thread that drops it to zero sees all other threads' writes before it destroys the object. shared_ptr's control block works this way.

Mutex, fine-grained locks or lock-free: how do you choose?

Start with one mutex and measure. Split locks if contention shows up and the structure has independent parts (head and tail of a queue, buckets of a table). Go lock-free only for a proven bottleneck and with a known-correct design, because memory reclamation and ABA make it hard; an SPSC ring buffer is the one case simple enough to write confidently.
