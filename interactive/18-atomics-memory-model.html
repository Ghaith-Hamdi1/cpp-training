Compare-and-swap

Compare-and-swap is the building block of every lock-free update. compare_exchange(expected, desired) means: if the value still equals expected, set it to desired; otherwise load the current value into expected and fail.

compare_exchange_weakcompare_exchange_strong
spurious failuremay fail even when the value matchedfails only if the value really differed
useinside a retry loop (cheaper on some CPUs)a single attempt, no loop

Compiled: a CAS with a stale expected returned false and refreshed expected to the current value (99).

atomic_flag and a spinlock

std::atomic_flag is the one type guaranteed to be lock-free. With two calls it makes a spinlock: lock by looping on test_and_set, unlock with clear.

Spinlock is fineUse a mutex instead
very short critical sections on dedicated coresthe holder can be descheduled: spinners burn CPU for nothing
waiting is shorter than a context switchlong or blocking work under the lock
  • is_lock_free() says whether a type uses real atomic instructions; big structs fall back to a hidden lock.

The ABA problem

A CAS only checks that the value is equal to what you read. If it went A to B and back to A in between, the CAS succeeds, but the structure around the value may have changed completely, for example a node that was freed and reused.

FixIdea
version counterstore a counter next to the value and compare both (a tagged pointer)
hazard pointersthreads announce what they are reading so nobody frees it
epoch-based reclamationfree only when no thread can still hold an old reference

The ABA problem and safe memory reclamation are why writing a lock-free pop is hard. Prefer a mutex, or a proven library.

Cheat sheet

Answer aloud, then open.

std::atomic vs mutex?

An atomic makes operations on a single variable indivisible, usually lock-free and cheap. A mutex protects any critical section, including invariants over several variables, but may block. Use atomics for counters and flags, mutexes for compound state.

Is volatile a substitute for atomic?

No. volatile prevents some compiler optimisations but gives no atomicity and no inter-thread ordering. Using it for synchronization is a data race.

compare_exchange_weak vs strong?

Both set a value only if it still equals the expected one. weak may fail spuriously, so it belongs in a retry loop and is cheaper on some CPUs; strong fails only on a real mismatch and suits a single attempt. On failure they load the current value into expected.

What is the ABA problem?

A CAS succeeds because the value is A again, but it went A to B to A in between, and the structure around it changed (for example a node was freed and reused). Fix with a version counter beside the pointer, or hazard pointers or epoch reclamation.

When is a spinlock appropriate?

For very short critical sections on dedicated cores where waiting is shorter than a context switch. It burns CPU while waiting and is dangerous if the holder can be descheduled. Otherwise use a mutex.
