Atomics and the Memory Model

Atomic operations, compare-and-swap, memory orders and happens-before with a simulator, the ordering patterns that matter, and thread-safe data structures from fine-grained locks to lock-free. Builds on Multithreading.

Atomic operations and compare_exchange

std::atomic<T> makes operations on one variable indivisible, usually without blocking. The increment is now one step:

Use an atomic forDo not use it for
a counter, flag, swapped pointer, statisticsan invariant over several variables: use a mutex

Compare-and-swap (CAS)

compare_exchange(expected, desired): "if the value still equals expected, set it to desired; otherwise load the current value into expected and fail". It is the building block of every lock-free update.

compare_exchange_weakcompare_exchange_strong
spurious failuremay fail even when the value matchedfails only if the value really differed
useinside a retry loop (cheaper on some CPUs)a single attempt, no loop

Compiled: a CAS with a stale expected returned false and refreshed expected to the current value (99).

atomic_flag and a spinlock

atomic_flag is the one type guaranteed lock-free. Four threads each doing 50,000 increments under this spinlock reached exactly 200,000 (compiled). A spinlock burns a core while waiting: fine for tiny critical sections on dedicated cores, bad when the lock holder can be descheduled (use a mutex).

volatile is NOT thread-safeIt only stops the compiler optimising an access away. No atomicity, no ordering. Use std::atomic.
  • is_lock_free() says whether the type is done with real atomic instructions; big structs fall back to a hidden lock.
  • ABA problem: a CAS can succeed when the value went A to B and back to A, although the world changed meanwhile. Fix with a version counter next to the value, or hazard pointers.

Memory orders and happens-before

Compilers and CPUs reorder memory operations, and each core has buffers and caches, so one thread's write may become visible to another thread later, or after a write that came after it. A plain int gives no guarantee. Atomics let you say how much ordering you need.

The one rule to learn: release and acquire

  • A release store publishes: every write the thread made before it becomes visible to any thread that reads the stored value with an acquire load.
  • The release/acquire pair synchronizes-with, and that creates a happens-before edge: data = 42 happens before the consumer's read, so the read is not a data race and sees 42.
  • happens-before is the formal "must be visible" relation. Within one thread it is program order; across threads it comes only from synchronization (atomics, mutexes, join, futures).

x86 hides bugsx86 already gives release/acquire for ordinary loads and stores, so wrong orderings often "work" on a developer's PC and fail on ARM (phones, Apple silicon, many servers). The simulator above shows what the C++ model allows, not what x86 does.
  • Both sides must take part: a release store read by a relaxed load publishes nothing.
  • A fence (std::atomic_thread_fence) gives the ordering without tying it to one variable. Know it exists; reach for acquire/release on the atomic first.
  • Without any synchronization, two threads touching the same non-atomic variable (one writing) is a data race: undefined behaviour, not merely "stale data".
Interview angle"What does acquire/release guarantee?" Everything written before the release is visible after the matching acquire. Say synchronizes-with and happens-before, and that seq_cst is the safe default.

Double-checked locking (the classic trap)

Without the release/acquire pair, another thread could see the pointer before the constructor's writes. In practice use a function-local static or std::call_once and let the compiler do this.

Be honest in interviewsStart with a mutex or seq_cst, measure, and weaken orders only when you can say which happens-before edge each one provides. "I use acquire/release for publication, relaxed for counters" is the answer interviewers want.

Thread-safe data structures

Three levels, in the order you should try them:

LevelHowExample
1. One coarse locka mutex around the whole structurea stack or map with a mutex (see the interface races in Multithreading)
2. Fine-grained locksdifferent mutexes for different parts, so threads that touch different parts do not waita queue with a head mutex and a tail mutex; a hash table with one mutex per bucket
3. Lock-freeatomics and CAS loops, no mutexa Treiber stack, an SPSC ring buffer

Fine-grained: a queue with two locks

The dummy node is the trick: with it, a push only touches the tail and a pop only the head, so one producer and one consumer never block each other. Compiled: a producer pushing 1 to 1000 and a consumer popping them summed to 500500.

Read-mostly: a lookup table

A price table read by many threads and updated rarely: std::shared_mutex with shared_lock for readers and unique_lock for writers (Other mutex types). Return copies or small values, never references into the table.

Lock-free: a stack push

Compiled: four threads pushing 1000 nodes each gave 4000 nodes, no lock. Pop is the hard part: another thread may pop and delete the node you are reading (memory reclamation), and the ABA problem can corrupt the list. Real implementations need hazard pointers, epochs or a counted pointer.

Lock-free is not faster by defaultA contended CAS loop can be slower than a mutex, and a bug shows up once a month on a customer machine. Use a mutex first, measure, and use a proven library (or the SPSC ring when one producer and one consumer is enough) before writing your own.
  • Wait-free (every thread finishes in a bounded number of steps) is stronger than lock-free (some thread always makes progress) which is stronger than obstruction-free.
  • Design the interface first: whole operations (tryPop returning an optional), not empty() then pop().

Interview cheat sheet

Say each answer aloud, then open it.

std::atomic vs mutex?

An atomic makes operations on a single variable indivisible, usually lock-free and cheap. A mutex protects any critical section, including invariants over several variables, but may block. Use atomics for counters and flags, mutexes for compound state.

Is volatile a substitute for atomic?

No. volatile prevents some compiler optimisations but gives no atomicity and no inter-thread ordering. Using it for synchronization is a data race.

What are the memory orders?

seq_cst (default, strongest, one global order), acquire/release (pair a release store with an acquire load to publish data), acq_rel for read-modify-write, and relaxed (atomicity only). Start with the default; weaken only with a reason and a clear happens-before argument.

What does release/acquire guarantee?

Everything the producer wrote before a release store is visible to a thread that reads the stored value with an acquire load. The pair synchronizes-with, which gives a happens-before edge, so the earlier plain writes are not a data race.

What does happens-before mean?

If A happens-before B, then A's effects are visible to B. Within a thread it is program order; between threads it exists only through synchronization: atomics with matching orders, mutex unlock/lock, thread start and join, futures. Two conflicting accesses without a happens-before relation are a data race.

When is relaxed enough?

When no other data depends on the atomic: a statistics counter, an id generator, a shutdown flag that carries no data. The final value is correct, but it orders nothing else.

Why can code with a wrong memory order work on x86 and fail on ARM?

x86's hardware already orders ordinary loads and stores like release/acquire, so missing orderings are hidden. ARM and POWER reorder far more, so the same code can read stale data there. The C++ model, not the PC you tested on, defines correctness.

compare_exchange_weak vs strong?

Both set a value only if it still equals the expected one. weak may fail spuriously, so it belongs in a retry loop and is cheaper on some CPUs; strong fails only on a real mismatch and suits a single attempt. On failure they load the current value into expected.

What is the ABA problem?

A CAS succeeds because the value is A again, but it went A to B to A in between, and the structure around it changed (for example a node was freed and reused). Fix with a version counter beside the pointer, or hazard pointers or epoch reclamation.

When is a spinlock appropriate?

For very short critical sections on dedicated cores where waiting is shorter than a context switch. It burns CPU while waiting and is dangerous if the holder can be descheduled. Otherwise use a mutex.

How is a reference count made thread-safe, and with which orders?

With an atomic counter: increments can be relaxed, the decrement is acq_rel so the thread that drops it to zero sees all other threads' writes before it destroys the object. shared_ptr's control block works this way.

Mutex, fine-grained locks or lock-free: how do you choose?

Start with one mutex and measure. Split locks if contention shows up and the structure has independent parts (head and tail of a queue, buckets of a table). Go lock-free only for a proven bottleneck and with a known-correct design, because memory reclamation and ABA make it hard; an SPSC ring buffer is the one case simple enough to write confidently.
