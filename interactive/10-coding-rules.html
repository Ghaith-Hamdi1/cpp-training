Coding Rules and Safe C++

In safety-related domains such as automotive, you are not free to use every C++ feature in every way. Coding guidelines restrict the language to a safer subset and tools check them automatically. This lesson explains what they are, why they exist, and the kinds of rules you will meet.

Why coding rules exist

C++ lets you write code that compiles but has undefined, unspecified or implementation-defined behaviour, or is simply easy to misread. In a car or medical device, a rare misbehaviour is not acceptable, so projects agree on rules that remove the risky corners.

Coding rules come in two kinds:

KindPurposeExamples
Guidelines (language usage)Avoid errors from using language features in vulnerable or unclear waysinitialise every variable; no C-style casts; no unchecked implicit narrowing
Style (form)Make code uniform and tidy so reviews are about logicindentation, brace position, naming of classes, functions and members

Everyone on the project must know the rules and follow them, and rules are only useful if they are checked automatically.

MISRA and AUTOSAR C++14

  • MISRA C / MISRA C++ are among the best-known rule sets. They began in the automotive industry and are now used widely in safety-critical embedded work. MISRA C++:2008 targets C++03.
  • AUTOSAR C++14 is a guideline for using C++14 in safety-related and critical environments. It is based on MISRA C++:2008 and other leading standards, updated for modern C++ (smart pointers, move semantics, constexpr and so on).
  • Both classify rules by strictness (for example required versus advisory) and let a project record a justified deviation when a rule must be broken.
  • Standards keep evolving (MISRA C++:2023 was written to supersede both MISRA C++:2008 and AUTOSAR C++14), so always check which version your project mandates.
Say this in an interview"I follow the project's coding standard, such as AUTOSAR C++14, check it with a static analyser in CI, and document any deviation with a reason rather than silently working around the tool."

Typical rules, and why

The exact rule numbers differ between standards, so learn the themes. Each one below is a pattern that is legal C++ but risky. Try to name the problem before you open each answer.

What is wrong?Reading an uninitialised local is undefined behaviour. Rule theme: initialise every object before use (int count{};).
What is wrong?A C-style cast hides which conversion happens and can do dangerous ones silently. Rule theme: use the named casts (static_cast and so on) so the intent is visible and greppable, and avoid reinterpret_cast and const_cast.
What is wrong?Manual ownership leaks on early returns and exceptions. Rule theme: manage resources with RAII: std::make_unique<Widget>(), containers, no naked new/delete. Many embedded standards go further and forbid dynamic allocation after start-up, to avoid fragmentation and unpredictable timing.
What is wrong?Values change silently or overflow. Rule themes: no implicit narrowing (use brace-initialisation uint8_t level{300}; which the compiler rejects), use fixed-width types, and check arithmetic that can overflow.
What is wrong?Recursion depth depends on the data, so stack usage cannot be bounded and may overflow. Embedded and safety rules commonly forbid recursion and require loops with a provable upper bound.
What is wrong?It pollutes the global namespace of every includer and can silently change overload resolution. Rule theme: never put using namespace in a header.
What is wrong?The compiler-generated copy copies the pointer, so two objects delete the same memory (double free). Rule theme: rule of zero / rule of five. Prefer std::vector<char> and write no special members, or define or delete all five.

Static analysis and tooling

Rules are verified by static code analysers that read the source without running it. Examples named in industry include cppcheck (free), clang-tidy (free, with checks aligned to several guidelines) and commercial tools such as CodeSonar, Polyspace or Helix QAC that map findings to MISRA or AUTOSAR rule IDs.

LayerWhat it catches
Compiler warnings (-Wall -Wextra -Werror)Many beginner mistakes immediately, at no cost. Turn them on first.
Static analyser in CIRule violations, null dereferences, leaks, dead code across the whole code base
Formatter (clang-format)Style, so nobody argues about braces in reviews
Sanitisers and testsWhat static analysis cannot prove: run-time behaviour (-fsanitize=address,undefined)
A clean report is not a proofStatic analysers give false positives and miss things. They reduce risk; they do not replace design, review and testing.

Interview cheat sheet

What is MISRA, and how does AUTOSAR C++14 relate to it?MISRA is a family of coding guidelines for safe use of C and C++ in critical systems. AUTOSAR C++14 is a guideline for C++14 in safety-related environments, based on MISRA C++:2008 and updated for modern C++.
Why would a safety standard forbid recursion?Stack depth cannot be bounded statically, so overflow is possible; an iterative version with a bounded loop can be analysed.
Why avoid dynamic allocation in embedded real-time code?Allocation time is unpredictable, the heap can fragment, and allocation can fail at run time. Allocate once at start-up or use fixed-size pools.
What is the difference between a coding guideline and a code style?Guidelines restrict how language features are used to avoid errors. Style fixes the appearance of the code: indentation, brace placement, naming.
You must break a rule. What do you do?Record a justified deviation through the project's process (comment plus tool suppression referencing it), get it reviewed, and keep it as narrow as possible.
