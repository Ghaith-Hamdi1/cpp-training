Futures, async and Promises

Running work in the background and getting the result back: std::async and std::future, exceptions that travel, promise, shared_future and packaged_task. Assumes Condition Variables.

Why tasks instead of raw threads

A std::thread runs a function but gives nothing back. To return a value you would need a shared variable, a mutex and a signal; to report an error you would need to catch it in the thread. A task packages all three: it runs a function, delivers the result later through a std::future<T> and passes any exception on to whoever asks for the result.

resultnone: use a shared variablefuture.get()

when the work is not yet donejoin() onlywait(), wait_for(), get()
controlfull: pinning, detachless: the library chooses
Prefer tasksUse tasks for "compute this and give me the answer". Use a raw thread for a long-lived worker you manage yourself.

std::async and std::future

std::async starts the function, normally on another thread, and returns a std::future. Call get() when you need the answer.

CallDoes
f.get()waits, then returns the value (or rethrows), once
f.wait()waits, does not take the value
f.wait_for(100ms)waits up to a time: ready, timeout or deferred
f.valid()true until get() has been called
Say launch::asyncThe default policy may defer the call until get(), so nothing runs in parallel. Pass std::launch::async when you want a thread.

The future that waits in its destructor

One surprise catches almost everyone. The future returned by std::async blocks in its destructor until the task is finished. If you throw the future away, the call is silently synchronous.

Future fromDestructor
std::async (launch::async)blocks until the task completes
std::promise, packaged_taskdoes not block

This is why std::async is not a drop-in fire-and-forget. For work that must run without being waited on, use a pool or a detached design, and think about shutdown.

Exceptions travel with the result

An exception in a plain thread kills the program. In a task it is caught, stored and rethrown when you call get(), so error handling stays where the result is used.

promise: the writing end

Sometimes you manage the thread yourself and still want a result channel. A std::promise is the writing end: the worker calls set_value (or set_exception) once, and the waiting thread gets it from the matching future.

Waiting with a time limit

Waiting forever is rarely what you want. wait_for and wait_until return a status instead of blocking without limit.

Result of wait_forMeaning
future_status::readythe value or exception is there: get() will not block
future_status::timeoutnot ready yet: do something else and ask again
future_status::deferredthe task has not started: it runs on get() (default launch policy)

Cheat sheet

Answer aloud, then open.

std::async vs std::thread?

async returns a future carrying the result and any exception, and may use a pool or defer execution (use launch::async to force a thread). thread gives raw control with no result channel. A future from async blocks in its destructor.

What are promise, future and packaged_task?

A promise is the write end of a one-shot channel, a future the read end. A packaged_task wraps a callable and fulfils a future with its result or exception, which is how a pool returns results. A shared_future is a copyable read end for several waiters.

How would you signal several threads to start at the same moment?

A promise<void> whose shared_future every thread waits on, or a std::latch/barrier. The promise is one-shot; for repeated signals use a condition variable.

Why does a discarded std::async future make the call synchronous?

The future returned by async waits for its task in its destructor. A temporary is destroyed at the end of the statement, so the statement blocks until the task has finished.

How does an exception from a task reach the caller?

It is caught inside the task, stored in the shared state, and rethrown by future::get().
