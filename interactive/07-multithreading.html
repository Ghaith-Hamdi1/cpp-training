Multithreading in C++

Threads, mutexes, deadlocks, atomics, condition variables, futures and thread pools, with simulators that let you create each bug yourself. Named in the job description, so this is the highest-value lesson.

How to study thisNew to threads? Do sections 1 to 6 first, then 7 to 10. Run every simulator. Compile examples with g++ -std=c++17 -pthread.

Why threads? The mental model

A thread is an independent flow of execution. Several threads make progress at once, like several cooks in one kitchen.

TermMeaning
Concurrencytasks in progress at overlapping times (can be interleaved on one core)
Parallelismtasks running at the same instant on different cores

Why: speed (use all cores), responsiveness (keep a UI or network handler alive), hiding I/O waits. Cost: about 1 MB stack each, startup time, context switches. Use threads only where the gain is measurable.

The whole difficultyThreads share memory, and the OS can switch between them between any two instructions.

Rules

  • Always join() or detach() before the std::thread is destroyed, otherwise std::terminate. A detached thread must not touch anything that may be destroyed.

  • Threads are move-only: std::thread b = std::move(a);.
  • An exception escaping the thread function calls std::terminate. Catch inside, or pass it out with a future.

CaveatThe simulator switches far more often than a real OS. A real race may fail once in thousands of runs, which is why it survives testing.
Data race = undefined behaviorTwo threads access the same memory, at least one writes, no synchronization. A race condition is the wider timing-dependent logic bug.

Why it hurts: shared data has an invariant (links agree, count matches items). An update breaks it briefly, and a thread looking then sees corruption. Trouble starts when two or more pieces of data change together.

Protecting a class

Good locking
  • Keep critical sections short; do slow work (I/O, computation) outside.
  • Mutex next to its data; never hand out references to that data.
  • Never call unknown code (callbacks, virtuals) while locked.
  • Too much locking means contention: the program becomes serial.

Fix: offer whole operations

Why does std::stack split top() and pop()? If pop() returned by value and the copy threw after removal, the element would be lost. A concurrent version must merge them: out-parameter, std::optional, shared_ptr<T>, or a non-throwing move.

Same pattern elsewhere:

Interview angle"Mutex in every method, so thread-safe?" No: each call is safe, the caller's sequence is not. Provide combined operations like try_pop and protect the whole invariant.

Deadlock

A deadlock: threads wait for each other forever. A holds a wants b; B holds b wants a. Step A once, B once, then try to go on:

"Run 500 random schedules": many end in deadlock. In real programs it may occur once in a million runs, only in production.

It needs all four (Coffman conditions); remove one and it cannot happen:

  1. Mutual exclusion: one holder at a time
  2. Hold and wait: holds one lock, waits for another
  3. No preemption: a lock cannot be taken away
  4. Circular wait: A waits for B, B for A

Fix: one global lock order

If every thread takes a before b, no cycle is possible:

Four guidelines, one idea

Do not wait for a thread that might be waiting for you.

  1. Avoid nested locks. If you need several, take them in one step with std::scoped_lock.
  2. No user-supplied code under a lock. A callback may take another lock, or keep a pointer to your data: Never pass out a pointer or reference to protected data.
  3. Fixed lock order. Hand-over-hand locking on list nodes deadlocks when two threads walk in opposite directions. Fix the traversal direction.
  4. Lock hierarchy. Each mutex has a level; a thread may only lock a lower level than it holds. Violations throw the first time, even if the unlucky timing never occurs.
No mutex neededTwo threads that join() each other deadlock, as does any cycle of futures or condition-variable waits.
Interview angle"Prevent deadlock?" Global lock order; std::scoped_lock; no foreign code under a lock; short locks; no nesting; try_lock with back-off. Re-locking a non-recursive mutex you own is undefined behavior.

Compilers and CPUs reorder memory operations; a plain int is not guaranteed visible to other threads. Atomics take a memory order:

Condition variables

To wait until something happens, a busy loop burns 100% CPU. A condition variable lets the thread sleep until woken, always together with a mutex and the shared state.

Watch the hand-over:

Three rules interviewers check

  1. Always wait with a predicate. Spurious wakeups happen, and another consumer may take the item first.
  2. Change the state under the mutex, then notify. Otherwise a lost wakeup: the waiter sees false, you notify, it then sleeps forever.
  3. The waiter needs unique_lock: wait unlocks while sleeping.

notify_one() wakes one waiter; notify_all() wakes all (shutdown, or several may proceed).

Futures and async

To run a function in the background and get its result later, use a std::future<T>.

  • f.get() blocks until ready (once only); wait() and wait_for() do not take the value.
  • Exceptions travel: a throwing task rethrows from f.get().
  • Prefer tasks to raw threads: std::thread has no result channel and terminates on exceptions.
  • Pass std::launch::async; the default may defer the call to get().
  • An async future blocks in its destructor, so a discarded one makes the call effectively synchronous.

std::packaged_task routes a function's result into a future (how pools return results).

Thread pools and producer/consumer

A thread per task is expensive and thousands overload the scheduler. A thread pool starts N workers once; tasks go in a queue (producer/consumer).

It combines everything: mutex, condition variable, stop flag, RAII shutdown. The task runs outside the lock, or only one could run at a time.

Sizing: CPU-bound, about hardware_concurrency() workers (more is oversubscription); I/O-bound, more.

Lock-free: SPSC ring buffer

With one producer and one consumer, two atomic indices need no lock: each is written by one thread, release/acquire publishes the data. A staple of low-latency code.

Be honest in interviewsStart with a mutex queue, measure, go lock-free only if the lock is the bottleneck. SPSC is the one case simple enough to write confidently.

Debugging and common bugs

Timing bugs vanish under a debugger or a printf ("Heisenbug"). Use tools:

  • ThreadSanitizer: -fsanitize=thread -g finds data races and prints both accesses. Run tests with it.
  • Helgrind / DRD (Valgrind): races and lock-order violations.
  • Thread ids in logs; gdb thread apply all bt on a hang.

Vocabulary

  • Thread-safe: usable from several threads without external locking (shared_ptr's reference count, not its pointee).
  • thread_local: one copy per thread.
  • Function-local static init is thread-safe since C++11 (Meyers Singleton).
  • std::call_once(flag, fn): initialize exactly once.

Interview cheat sheet

Say each answer aloud, then open it.

What is the difference between a process and a thread?

A process has its own address space; threads of one process share memory but each has its own stack and registers. Thread creation and switching are cheaper, communication is easy (shared memory) but needs synchronization.

What is a data race? Is it the same as a race condition?

A data race is unsynchronised concurrent access to the same memory with at least one write: undefined behavior in C++. A race condition is the wider class of bugs where correctness depends on timing, which can exist even without a data race (two correctly locked steps that needed to be one atomic operation).

What happens if a std::thread is destroyed while still joinable, and why?

std::terminate is called. The alternatives are worse: an implicit join can hide long waits, and an implicit detach leaves a running thread using locals that may be gone (undefined behavior). So make the thread unjoinable on every path: join in an RAII guard, or use std::jthread (C++20), which joins automatically.

lock_guard vs unique_lock vs scoped_lock?

lock_guard: simplest RAII lock for a scope. unique_lock: flexible (unlock/relock, deferred, movable) and needed by condition variables. scoped_lock (C++17): locks multiple mutexes at once with deadlock avoidance.

What is a deadlock and how do you prevent it?

Threads wait for each other's locks forever. Needs mutual exclusion, hold-and-wait, no preemption and circular wait. Prevent with a consistent global lock order, std::scoped_lock/std::lock for multiple mutexes, short critical sections, no calls to foreign code under a lock, or try_lock.

Why does condition_variable::wait need a predicate / a loop?

Spurious wakeups (a thread may wake without a notification) and because the state may change again between the notification and the thread reacquiring the lock. The predicate re-checks the real condition.

Why must the shared condition be modified under the mutex?

Otherwise the waiter could check the condition (false), then the notifier changes it and notifies, then the waiter goes to sleep: a lost wakeup. The mutex makes check-and-sleep atomic with respect to the update.

std::atomic vs mutex?

An atomic makes operations on a single variable indivisible, usually lock-free and cheap. A mutex protects any critical section, including invariants over several variables, but may block. Use atomics for counters and flags, mutexes for compound state.

Is volatile a substitute for atomic?

No. volatile prevents some compiler optimisations but gives no atomicity and no inter-thread ordering. Using it for synchronization is a data race.

What are the memory orders?

seq_cst (default, strongest, one global order), acquire/release (pair a release store with an acquire load to publish data), relaxed (atomicity only). Start with the default; weaken only with a reason and a proof.

std::async vs std::thread?

async returns a future carrying the result and any exception, and may use a pool or defer execution (use launch::async to force a thread). thread gives raw control with no result channel. A future from async blocks in its destructor.

What is false sharing?

Threads writing different variables on the same cache line force the line to bounce between cores, slowing everything. Fix by padding or aligning per-thread data to the cache line size (alignas(64)).

Why avoid locks and heap allocation on a real-time hot path?

Both can block or take unpredictable time (contention, priority inversion, allocator locks). Use preallocated buffers and pools, per-thread data and lock-free structures such as an SPSC ring buffer to keep latency bounded.

Is a function-local static initialised thread-safely?

Yes, since C++11 initialization happens exactly once even with concurrent callers ("magic statics"). That is why the Meyers Singleton is thread-safe. Using the object afterwards still needs its own synchronization.

My class locks a mutex in every method. Is it thread-safe?

Not necessarily. Each call is safe on its own, but a caller's sequence of calls is not atomic. The classic case is a shared stack: if (!s.empty()) { v = s.top(); s.pop(); } races, because another thread can pop between the check and the use. The cause is the interface (it is also true of a lock-free stack), so the fix is to provide whole operations such as std::optional<T> try_pop() that check and remove under one lock.

Can threads deadlock without any mutex? What are the practical rules against deadlock?

Yes: two threads that join() each other, or any cycle of waits on futures or condition variables. The rules all mean "do not wait for a thread that might be waiting for you": avoid nested locks (or take several with scoped_lock), never call user-supplied code or leak references to protected data while holding a lock, lock in a fixed order, and use a lock hierarchy so a wrong order is caught immediately at runtime.

How would you find a data race in a large program?

Build and run the tests with ThreadSanitizer (-fsanitize=thread), and Helgrind for lock-order problems; review shared state and make sure every access has a lock or is atomic; reduce sharing by design.
