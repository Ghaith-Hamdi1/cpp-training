Multithreading in C++

From "what is a thread?" to mutexes, deadlocks, atomics, condition variables, futures and thread pools, with simulators that let you create each bug yourself. No prior knowledge assumed. Multithreading is named in the job description, so this is the highest-value lesson in the set.

How to study thisIf it is all new, do sections 1 to 6 carefully first (threads, races, mutexes, interface races, deadlocks): that is the core that interviews probe. Then read 7 to 10. Run every simulator, because the bugs only make sense once you have watched them happen. All examples assume #include <thread>, <mutex> etc. and compile with g++ -std=c++17 -pthread.

Why threads? The mental model

A normal program has one thread of execution: one cook working through a recipe, one instruction at a time. A thread is an independent flow of execution. A program can have many, so several things can progress at once, like several cooks in one kitchen.

TermMeaning
Processa running program with its own private memory. Processes are isolated from each other.
Threada flow of execution inside a process. Threads of one process share the same memory (heap and globals) but each has its own stack and registers.
Concurrencyseveral tasks in progress at overlapping times (can be interleaved on a single core).
Parallelismseveral tasks running at literally the same instant on different cores.

Why use threads? (1) Speed: split heavy work across cores. (2) Responsiveness: keep a UI or a network handler alive while a slow job runs. (3) Waiting: do other work while one thread blocks on I/O.

The whole difficulty in one sentenceThreads share memory, and the operating system may switch between them at any moment, between any two instructions. Everything in this lesson is about keeping shared memory correct despite that.

The rules you must know

  • Always join() or detach() before the std::thread object is destroyed. If a thread is still joinable when its object dies, the program calls std::terminate. join() waits for it. detach() lets it run on its own; then you can no longer wait for it, and it must not touch anything that might be destroyed.
  • Arguments are copied into the thread. To share a variable by reference you must say so with std::ref.
  • Threads are move-only: std::thread b = std::move(a);.
  • An exception that escapes a thread's function calls std::terminate. Catch inside the thread (or pass it out with a future, see later).
The classic detach bug Capture by value (or join()) whenever the thread could outlive the variable.

Shared data and data races

Two threads each add 1 to a shared counter. What could go wrong?

The statement ++counter looks like one step but the CPU performs three:

  1. load the value from memory into a register: r = counter
  2. add one to the register: r = r + 1
  3. store the register back to memory: counter = r

If thread B's load happens between thread A's load and store, both start from the same old value, both write the same new value, and one increment is lost. Try to make it happen. Click Step A and Step B in any order you like (you are playing the operating system's scheduler):

A realistic caveatThe simulator may switch threads between every pair of instructions, far more often than a real operating system does, so it makes the bug look very common. On a real machine the same race might fail once in thousands of runs, which is exactly why these bugs survive testing and bite in production.
Data race = undefined behaviorA data race is two threads accessing the same memory at the same time, with at least one writing and no synchronization. In C++ this is undefined behavior, not merely "a slightly wrong number": the compiler and CPU may reorder things in ways that make the program do anything. A race condition is the broader logic bug where the result depends on timing.

Three ways to be safe

StrategyHow
1. Do not shareeach thread works on its own data (local variables, thread_local), and you combine results afterwards. The best option when possible.
2. Share, but never modifyread-only data (const) is safe to read from many threads.
3. Share and protectuse a mutex (next section) or an atomic so only one thread changes the data at a time.

Mutexes: taking turns

A mutex (mutual exclusion lock) lets only one thread at a time execute a protected region, the critical section. A thread calls lock(); if another thread holds the lock, it waits. Always use RAII locks, never raw lock()/unlock()

If code between a manual lock() and unlock() throws or returns early, the mutex stays locked forever and every other thread freezes. The RAII wrappers unlock in their destructor no matter how the scope is left:

TypeUse it when
std::lock_guard<std::mutex>the simple default: lock for the whole scope
std::unique_lock<std::mutex>you need to unlock early, relock, defer locking, or use a condition variable (required for cv.wait)
std::scoped_lock (C++17)locking several mutexes at once without deadlock
std::shared_mutex + shared_lockmany readers or one writer, when reads vastly outnumber writes

Protecting a class properly

Rules for good locking
  • Keep critical sections short: lock, touch the shared data, unlock. Do the slow work (I/O, computation) outside the lock.
  • Put the mutex next to the data it protects, inside the same class, and never hand out references to that data.
  • Never call unknown code (callbacks, virtual functions) while holding a lock: it may try to take the same lock, or another one.
  • Locking costs time. If every access is locked, threads queue up and you get contention: your parallel program becomes serial.

Races hidden in interfaces

Two things can go wrong with this interleaving, and both are logic errors that no amount of internal locking can prevent:

  • B calls top() on an empty stack: undefined behavior. Its earlier empty() answer was true when given, stale one moment later.
  • If both threads read top() before either calls pop(), the same element is processed twice while the stack loses only one.

This is a check-then-act race (sometimes called time-of-check to time-of-use). It is not specific to mutexes: a lock-free stack with the same interface has the same problem. The cause is the interface, so the cure is to change the interface.

Why does std::stack split top() and pop() in the first place? If pop() returned the element by value, and copying it threw an exception after the element was already removed, that element would be lost. That is why the single-threaded design separates them. A concurrent version has to merge them, so the usual solutions are to hand the value out through an out-parameter or std::optional, to return a std::shared_ptr<T>, or to require that the element type's move or copy cannot throw.

The same pattern shows up everywhere. All of these are check-then-act races when only the individual calls are locked:

Racy sequenceWhole-operation fix

Interview angle"I added a mutex to every method, so is my class thread-safe?" Not necessarily. Each method is safe, but the caller's sequence of calls is not. Protect the whole invariant: provide combined operations such as try_pop, and design the interface so that callers never need to check and act separately.

Deadlock

A deadlock is when threads wait for each other forever. The classic recipe: thread A holds lock a and wants b, while thread B holds b and wants a. Neither can proceed. Here the two threads take the locks in opposite order. Try to deadlock them by hand: step A once (takes a), step B once (takes b), then try to go on.

Press "Run 500 random schedules": a large share of runs end in a deadlock. In real programs it is worse: it may happen once in a million runs, always in production, and never under the debugger.

A deadlock needs all four of these (the Coffman conditions), so removing any one prevents it:

  1. Mutual exclusion: the resource can be held by only one thread.
  2. Hold and wait: a thread holds one lock while waiting for another.
  3. No preemption: a lock cannot be taken away from its holder.
  4. Circular wait: A waits for B, B waits for A (a cycle).

Four guidelines that all say the same thing

Every deadlock-avoidance rule boils down to one idea: do not wait for another thread if there is any chance it is waiting for you. The practical guidelines are ways of making sure that cannot happen:

  1. Avoid nested locks. If a thread never holds more than one lock, locks alone cannot deadlock. When you truly need several, take them in a single step with std::scoped_lock (or std::lock).
  2. Do not call user-supplied code while holding a lock. A callback, a virtual function or an operation on a template parameter could do anything, including taking another lock (a hidden nested lock) or, worse, keeping a pointer to your protected data: Rule: never pass out a pointer or reference to protected data, whether by returning it, storing it somewhere visible, or giving it to code you do not control. The mutex only protects what is accessed through it.
  3. Acquire locks in a fixed order when you must hold several and cannot take them together. A classic trap is a mutex per node in a linked list with "hand-over-hand" traversal (lock the next node, then release the current one). Two threads walking in opposite directions meet in the middle holding each other's lock: deadlock. Fix it by fixing the traversal direction, so everyone locks nodes in the same order.
  4. Use a lock hierarchy. Give each mutex a numeric level and let a thread lock only a mutex whose level is lower than every lock it already holds. Then a cycle is impossible, and a violation is reported the first time the wrong order is attempted, even if the unlucky timing that would actually deadlock never happens in testing.
Deadlock needs no mutex at allTwo threads that each call join() on the other deadlock, and so does any cycle of threads waiting on each other's futures or condition variables. It applies to every kind of waiting, not just locks.
Interview angle"How do you prevent deadlock?" Impose a global lock ordering; lock multiple mutexes with std::scoped_lock; avoid holding a lock while calling out to other code; hold locks briefly; avoid nested locking when you can; or use try_lock with back-off. Also: locking a non-recursive mutex you already own is undefined behavior (in practice, a thread that deadlocks with itself).

Atomics

For a single simple variable, a mutex is overkill. std::atomic<T> makes operations on one variable indivisible: no other thread can see a half-finished update. It is implemented with special CPU instructions and usually does not block. Compare with the broken counter: the increment is now one single step.

Use an atomic forDo not use it for
a counter, a flag, a pointer you swap, statisticsan invariant that spans several variables (for example "balance and history must change together"). For that you need a mutex.

Memory ordering (what you need to know)

Compilers and CPUs reorder memory operations for speed. A plain int written by one thread has no guarantee of ever being visible to another. Atomics take an optional memory order to say how much ordering you need:

OrderMeaningUse
memory_order_seq_cst (default)strongest: all threads agree on one global order of atomic operationswhen in doubt. Simple and correct.
memory_order_release / acquirea release store makes everything the thread wrote before it visible to a thread that does an acquire load and sees that valuepublishing data with a flag
memory_order_relaxedatomicity only, no orderingplain counters and statistics
volatile is NOT thread-safeIn C++, volatile only stops the compiler optimising an access away (useful for hardware registers). It gives no atomicity and no ordering between threads. Use std::atomic.
Interview angleKnow: atomic vs mutex (lock-free single variable vs general critical section); is_lock_free(); that default seq_cst is the safe choice and weaker orders are an optimisation needing proof; and the ABA problem (a CAS succeeds because a value changed A to B and back to A, hiding that something happened; fixed with version counters or hazard pointers).

Condition variables

Sometimes a thread must wait until something happens: a consumer waits for the producer to put an item in a queue. Looping on while (queue.empty()) {} burns 100% CPU ("busy waiting"). A condition variable lets the thread sleep until another thread wakes it. It always works together with a mutex and the shared state it guards.

Three rules that interviewers check

  1. Always wait with a predicate (cv.wait(lk, pred)), which is the same as while (!pred()) cv.wait(lk);. The OS can wake a thread for no reason (spurious wakeup), and another consumer might have taken the item first, so the condition must be re-checked.
  2. Change the shared state while holding the mutex, then notify. If you modify it without the lock, a waiter can check the condition, see it false, and be about to sleep just as you notify: the notification is lost and it sleeps forever (lost wakeup).
  3. The waiter must hold a std::unique_lock (not lock_guard) because wait must unlock the mutex while sleeping and relock it on wake-up.

notify_one() wakes a single waiter; notify_all() wakes every waiter (use it when the condition may allow several to proceed, or for shutdown).

A reusable thread-safe queue

Futures and async

Often you do not want to manage a thread by hand: you just want to run a function in the background and get its result later. A std::future<T> is a placeholder for a value that will be ready in the future.

  • f.get() blocks until the result is ready, and it can be called only once. f.wait() waits without taking the value; f.wait_for(...) waits with a timeout.
  • Exceptions travel with the result: if the task throws, f.get() rethrows it in the calling thread. This is the clean way to report errors from threads.
  • Pass std::launch::async explicitly. With the default policy the implementation is allowed to defer the call and run it lazily (on the calling thread) only when you call get().
  • A future obtained from std::async blocks in its destructor until the task finishes. So std::async(...) with the returned future discarded runs the task effectively synchronously.

std::packaged_task wraps a function so that its result goes into a future, which is how thread pools return results from queued tasks.

Thread pools and producer/consumer

Creating a thread per task is expensive (tens of microseconds, plus memory for its stack) and creating thousands overloads the scheduler. A thread pool starts a fixed number of worker threads once. Tasks are put in a queue; each idle worker takes the next one. This is the producer/consumer pattern: producers submit work, consumers (workers) process it.

Read it once slowly, because it combines everything: a mutex protecting the queue, a condition variable to sleep and wake, a stop flag for graceful shutdown, and RAII in the destructor. Notice that the task runs outside the lock, otherwise only one task could ever run at a time.

Sizing: for CPU-bound work use about hardware_concurrency() workers (more just fight over cores: oversubscription). For work that mostly waits on I/O you can use more.

Performance and real-time concerns

Correct is step one. Fast and predictable is step two, and it is what matters for low-latency systems such as market-data feed handlers.

Lock-free: a single-producer single-consumer ring buffer

When exactly one thread produces and one consumes, you can pass data with no lock at all using two atomic indices. Each index is written by only one thread, so no conflict is possible; release/acquire makes the data visible. This pattern is a staple of low-latency code.

Be honest about lock-free in interviewsLock-free code is hard to write and verify. Say you would start with a mutex-based queue, measure, and move to a lock-free structure only if profiling shows the lock is the bottleneck. The SPSC queue is the one case simple enough to write confidently.

Debugging and common bugs

Threading bugs are timing-dependent: they vanish when you add a printf or run under a debugger (a "Heisenbug"). Use tools built to catch them:

  • ThreadSanitizer: compile and link with -fsanitize=thread -g (GCC or Clang). It detects data races at runtime and prints both conflicting accesses with stack traces. Run your tests with it routinely.
  • Helgrind / DRD (Valgrind): finds races and lock-order violations (potential deadlocks).
  • Logging with thread ids and timestamps, a core dump / gdb thread apply all bt to see where every thread is stuck in a hang.
SymptomLikely cause
Wrong totals, occasional crashes, "works on my machine"data race (missing lock or atomic)
Program hangs, CPU idledeadlock (or a lost wakeup / a thread waiting for a notification that already happened)
Program hangs, CPU 100%busy-wait loop, or a livelock (threads keep reacting to each other without progress)
Crash at exit, or on a detached threaddetached thread using destroyed data; thread still joinable at destruction (std::terminate)
Slower with more threadslock contention, false sharing, oversubscription
Garbled console outputseveral threads writing to std::cout: lines interleave. Build the whole line first and print once, or guard with a mutex.

Handy vocabulary

  • Thread-safe: can be used from several threads at once without external locking (for example, the atomic reference count of shared_ptr; not the object it points to).
  • thread_local: each thread gets its own copy of the variable. No sharing, no races.
  • Function-local static initialization is thread-safe since C++11 (the basis of the Meyers Singleton).
  • std::call_once(flag, fn): run initialization code exactly once across all threads.

Interview cheat sheet

Say each answer out loud, then open it to compare.

What is the difference between a process and a thread?

A process has its own address space; threads of one process share memory but each has its own stack and registers. Thread creation and switching are cheaper, communication is easy (shared memory) but needs synchronization.

What is a data race? Is it the same as a race condition?

A data race is unsynchronised concurrent access to the same memory with at least one write: undefined behavior in C++. A race condition is the wider class of bugs where correctness depends on timing, which can exist even without a data race (two correctly locked steps that needed to be one atomic operation).

What happens if a std::thread is destroyed while still joinable?

std::terminate is called. Always join() or detach(); std::jthread (C++20) joins automatically.

lock_guard vs unique_lock vs scoped_lock?

lock_guard: simplest RAII lock for a scope. unique_lock: flexible (unlock/relock, deferred, movable) and needed by condition variables. scoped_lock (C++17): locks multiple mutexes at once with deadlock avoidance.

What is a deadlock and how do you prevent it?

Threads wait for each other's locks forever. Needs mutual exclusion, hold-and-wait, no preemption and circular wait. Prevent with a consistent global lock order, std::scoped_lock/std::lock for multiple mutexes, short critical sections, no calls to foreign code under a lock, or try_lock.

Why does condition_variable::wait need a predicate / a loop?

Spurious wakeups (a thread may wake without a notification) and because the state may change again between the notification and the thread reacquiring the lock. The predicate re-checks the real condition.

Why must the shared condition be modified under the mutex?

Otherwise the waiter could check the condition (false), then the notifier changes it and notifies, then the waiter goes to sleep: a lost wakeup. The mutex makes check-and-sleep atomic with respect to the update.

std::atomic vs mutex?

An atomic makes operations on a single variable indivisible, usually lock-free and cheap. A mutex protects any critical section, including invariants over several variables, but may block. Use atomics for counters and flags, mutexes for compound state.

Is volatile a substitute for atomic?

No. volatile prevents some compiler optimisations but gives no atomicity and no inter-thread ordering. Using it for synchronization is a data race.

What are the memory orders?

seq_cst (default, strongest, one global order), acquire/release (pair a release store with an acquire load to publish data), relaxed (atomicity only). Start with the default; weaken only with a reason and a proof.

std::async vs std::thread?

async returns a future carrying the result and any exception, and may use a pool or defer execution (use launch::async to force a thread). thread gives raw control with no result channel. A future from async blocks in its destructor.

What is false sharing?

Threads writing different variables on the same cache line force the line to bounce between cores, slowing everything. Fix by padding or aligning per-thread data to the cache line size (alignas(64)).

Why avoid locks and heap allocation on a real-time hot path?

Both can block or take unpredictable time (contention, priority inversion, allocator locks). Use preallocated buffers and pools, per-thread data and lock-free structures such as an SPSC ring buffer to keep latency bounded.

Is a function-local static initialised thread-safely?

Yes, since C++11 initialization happens exactly once even with concurrent callers ("magic statics"). That is why the Meyers Singleton is thread-safe. Using the object afterwards still needs its own synchronization.

My class locks a mutex in every method. Is it thread-safe?

Not necessarily. Each call is safe on its own, but a caller's sequence of calls is not atomic. The classic case is a shared stack: if (!s.empty()) { v = s.top(); s.pop(); } races, because another thread can pop between the check and the use. The cause is the interface (it is also true of a lock-free stack), so the fix is to provide whole operations such as std::optional<T> try_pop() that check and remove under one lock.

Can threads deadlock without any mutex? What are the practical rules against deadlock?

Yes: two threads that join() each other, or any cycle of waits on futures or condition variables. The rules all mean "do not wait for a thread that might be waiting for you": avoid nested locks (or take several with scoped_lock), never call user-supplied code or leak references to protected data while holding a lock, lock in a fixed order, and use a lock hierarchy so a wrong order is caught immediately at runtime.

How would you find a data race in a large program?

Build and run the tests with ThreadSanitizer (-fsanitize=thread), and Helgrind for lock-order problems; review shared state and make sure every access has a lock or is atomic; reduce sharing by design.
