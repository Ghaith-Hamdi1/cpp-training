Low-Latency C++

How a feed handler keeps its hot path fast and predictable: measuring tail latency, avoiding allocation, cache-friendly data, order-book structures, queues between threads, and pinning threads to cores. Compiled examples are in examples/lessons/12-low-latency. Assumes Multithreading and Wire Formats and Parsing.

Where latency comes from

  • Latency is the time for one message to get through; throughput is how many per second. A system can have great throughput and terrible latency.
  • For a feed handler the tail matters: the rare slow case (once in a thousand) is what causes a stale book or a missed trade. Average time hides it.
  • So the goal is not only "fast" but predictable: remove anything whose cost can suddenly jump.

Measuring: percentiles and tail latency

  • Never judge by the average. Report percentiles: p50 (median), p99, p99.9, and the maximum. p99.9 means 1 in 1000 operations is at least that slow.
  • Collect every sample (do not average on the fly), sort afterwards, read the percentile by rank.

Measuring pitfalls

  • The compiler deletes unused work. If a benchmark's result is never used, the loop may be optimized away. Store results into a volatile sink, or print a checksum.
  • Warm up. The first iterations pay for cold caches and page faults. Discard them, or report them separately.
  • Do not disturb what you measure: no printing or allocation inside the timed region, and the clock call itself costs tens of nanoseconds.
  • Measure in realistic conditions (real message rates, other threads running). A quiet benchmark hides the stalls that matter.

Memory on the hot path

new and malloc can take a lock, walk free lists, call into the kernel for more memory and fragment the heap. Usually fast, but occasionally slow and unpredictable. The rule: allocate everything at startup; the hot path never calls new.

  • Preallocate containers: reserve() a vector so it never reallocates (one allocation instead of several as it grows).
  • Object pool: a fixed array of slots plus a free list. Allocation and release are a few instructions; if the pool is exhausted, you decide what to do (drop, count, wait).
  • Arena (std::pmr::monotonic_buffer_resource): allocation is "bump a pointer" inside a buffer you provide; everything is released at once.
  • Also: std::array and fixed buffers instead of std::string and std::vector for small data, and no std::function capturing large state (it may allocate).

Cache-friendly data

  • A cache line is 64 bytes. A cache miss to main memory costs about a hundred times a hit, so locality dominates: data used together should sit together.
  • Contiguous beats linked. std::vector and std::array stream through memory; std::list and std::map chase pointers to nodes scattered across the heap (each node is also a separate allocation).
  • AoS versus SoA. Array of structs keeps one record together (good when you use most fields); struct of arrays keeps each field together (good when a loop uses one or two fields). The program shows 40,000 bytes streamed to read all bids with AoS and 8,000 with SoA, with identical results.
  • Hot/cold split: keep fields used on every message together and small; move rarely used fields elsewhere (struct size and padding: Wire Formats).
False sharingTwo threads writing different variables on the same cache line make the line bounce between cores. Give each its own line: alignas(64) std::atomic<size_t> head_; alignas(64) std::atomic<size_t> tail_; (sizeof grows from 16 to 128 bytes, which is the point). Introduced in Multithreading.

Order books: choosing a structure

An order book keeps the resting quantity at each price on the bid side and the ask side, and updates it on every add, modify or cancel. The questions are always the same: update a level, find the best price, cancel by order id.

Queues between threads

Pipeline stages run on separate threads and hand messages over a queue. With one producer and one consumer (SPSC) no lock is needed: each index is written by exactly one thread (Multithreading).

  • Power-of-two capacity turns the wrap-around into index & (N - 1), one instruction, with free-running counters.
  • Padded indices (alignas(64)) so the two threads do not fight over one cache line.
  • Always bounded. An unbounded queue turns a slow consumer into growing memory and growing delay. When the queue is full you choose a policy:
PolicyBehaviorUse when
block (back-pressure)the producer waitsnothing may be lost, and the producer can afford to wait (not for a market-data reader)
drop newesttryPush returns false, count itsimple; the book will need a recovery
drop oldestoverwrite the oldest entryonly the latest data matters
conflatekeep only the latest update per instrumentslow consumers of quotes

The program runs two real threads over a 1024-slot ring with a drop-newest policy: received + dropped = 200000 and the consumer's sum equals the producer's, in 20 of 20 runs.

A predictable hot path

Besides memory and queues, a few language features add unpredictable cost. Keep them off the hot path:

Avoid on the hot pathWhyUse instead
exceptions (throw)a throw costs microseconds and its cost varies; unwinding tables add sizeerror codes, std::optional, a small result struct; validate at the boundary
virtual callsan indirect call: no inlining, harder for the CPU to predicttemplates, CRTP, std::variant with std::visit (decide the type at compile time)
locks (std::mutex)contention means waiting and context switchessingle-writer data, SPSC queues, atomics
logging and I/Osystem calls, formatting, locks inside the loggerpush a small record onto a queue; a background thread formats and writes
std::function, shared_ptrpossible allocation, an indirect call, an atomic reference counttemplates or function pointers, unique_ptr or plain ownership
std::map, std::list, std::string buildingallocation per node or per stringarrays, pools, fixed buffers, string_view
  • Mark functions that cannot throw noexcept; it lets the compiler skip unwinding code.
  • constexpr lookup tables move work to compile time; [[likely]] / [[unlikely]] (C++20) hint at the common path.
  • These rules are for the hot path. Startup, configuration and error reporting can use exceptions and heap freely.

Threads, cores and busy-polling

  • Pin each thread to a core (CPU affinity). The OS stops migrating it, so its caches stay warm and its timing steady. Give hot threads their own cores, and do not run more busy threads than cores (oversubscription causes context switches).
  • Busy-poll instead of blocking. A thread that sleeps on a condition variable pays a wake-up delay (microseconds) when work arrives. A thread that spins checking a flag reacts almost instantly but uses 100% of its core. Latency-critical threads spin; others block.
  • Memory placement: on multi-socket machines keep a thread and its data on the same NUMA node. Pre-touch (page-fault in) buffers at startup so the first use on the hot path does not take a page fault.
  • Isolating cores from the scheduler and tuning interrupts is an operating-system job, usually done by the platform team.

Interview cheat sheet

Answer aloud, then open.

Why does tail latency matter more than the average in a feed handler?

The rare slow case (p99.9) is what produces a stale book or a missed trade, and the average hides it: a mean of 281 ns can coexist with a p99.9 of 80 microseconds. Measure and report percentiles, and remove sources of unpredictable delay.

Why avoid new on the hot path, and what do you do instead?

The allocator can take a lock, walk free lists, fragment and call the kernel, so its cost is unpredictable. Allocate at startup: reserve containers, use an object pool or an arena (std::pmr::monotonic_buffer_resource), and use fixed buffers instead of strings and vectors for small data.

How does an object pool work?

A fixed array of slots, plus a free list threaded through the free slots. Allocation pops the head of the list and constructs the object there with placement new; deallocation destroys it and pushes the slot back. Both are a few instructions with no heap, and when the pool is empty the caller decides what to do.

Array of structs versus struct of arrays?

AoS keeps one record's fields together, good when you use most fields. SoA keeps each field in its own array, good when a loop uses one or two fields: it streams only the bytes it needs, so each cache line is fully useful. Same results, less memory traffic.

What is false sharing and how do you fix it?

Two threads writing different variables on the same 64-byte cache line force the line to bounce between cores. Give each variable its own line with alignas(64) or padding, as for the head and tail indices of an SPSC queue.

Why is a vector or array usually faster than std::map or std::list?

Contiguous memory is cache-friendly and prefetchable; node-based containers chase pointers across the heap and allocate per node. Big-O hides these constants, especially for small and medium sizes.

How would you structure an order book?

For a bounded price window, an array of quantities indexed by price tick: O(1) updates, no allocation, with the best price tracked and rescanned when its level empties. A hash map from order id to its price and quantity handles cancels. A std::map is simpler but allocates a node per level.

Why is an SPSC ring capacity a power of two?

The wrap-around becomes counter & (N - 1) instead of a modulo, one cheap instruction, and the head and tail counters can simply keep counting up while tail - head is the size.

What do you do when a queue between threads is full?

Never let it grow without bound. Choose a policy: block (back-pressure), drop the newest, drop the oldest, or conflate to the latest per instrument, count what was dropped, and recover from the gap if needed. A market-data reader normally cannot block.

Why avoid exceptions, virtual calls, locks and logging on the hot path?

Each adds cost that is large or unpredictable: a throw costs microseconds, a virtual call blocks inlining and is an indirect branch, a mutex can wait and context-switch, and logging means system calls and formatting. Use error codes, templates or CRTP, single-writer data, and an asynchronous logger fed by a queue.

Busy-polling versus blocking, and why pin threads?

Blocking saves CPU but a wake-up costs microseconds; busy-polling reacts almost immediately but burns a whole core, so only latency-critical threads spin. Pinning a thread to a core stops migration, which keeps its caches warm and its timing stable.
