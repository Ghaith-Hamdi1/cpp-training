Design Patterns in C++

Patterns are named, proven solutions to design problems that keep recurring. Interviewers use them to check that you can structure code, not just write it. This lesson covers the five you are most likely to be asked about (Singleton, Factory, Strategy, Observer, State), shows how modern C++ changes them, and ends with the SOLID principles behind them.

What patterns are and are not

A design pattern is a vocabulary: saying "this is an Observer" instantly conveys structure and intent to another developer. They come in three families:

FamilyConcerned withExamples
Creationalhow objects are createdSingleton, Factory, Builder
Structuralhow objects are composedAdapter, Decorator, Proxy, PIMPL
Behaviouralhow objects interact and share responsibilityStrategy, Observer, State, Command, Visitor
Patterns are not goalsDo not add a pattern for its own sake. Each one adds indirection, so use it only when it solves a real problem you have. A good answer in an interview always includes when not to use it.
Modern C++ shortens many of themA lambda or std::function often replaces a whole Strategy or Command class hierarchy. std::visit replaces the Visitor boilerplate. Smart pointers are a Proxy. RAII is a pattern the language supports directly. The ideas matter more than the class diagrams.

Singleton

Intent: guarantee that a class has exactly one instance and give global access to it (a logger, a configuration store, a hardware manager).

This is the Meyers Singleton. Step through it:

  • Thread safety: since C++11 the initialization of a function-local static is guaranteed to happen exactly once even if many threads call instance() at the same time ("magic statics"). You do not need a mutex or double-checked locking for the creation. Calls on the object itself (log) still need their own synchronization if they mutate shared state.
  • Lazy: it is built on first use, which also avoids the static initialization order problem between translation units.
  • Drawbacks (say these in the interview): it is global state in disguise; it hides dependencies (any code can reach it); it makes unit testing hard because you cannot substitute a fake; and destruction happens at program exit in an unspecified order relative to other statics, so using it from another static's destructor can touch a dead object.
  • Alternative: create one object in main and pass it (by reference) to the code that needs it: dependency injection. You still get "one instance" without the global.

Factory

Intent: create objects without the caller naming the concrete class. The caller asks for "a circle" (by an enum, string or config value) and receives something it can only use through an interface.

  • Return a smart pointer (unique_ptr) so ownership is clear and the caller cannot leak it. It converts to shared_ptr if needed.
  • The base class needs a virtual destructor, because the object is deleted through a Shape pointer.
  • Adding a new type means editing the factory. To avoid that (Open/Closed principle), keep a registry: std::map<std::string, std::function<std::unique_ptr<Shape>(double)>> that types register themselves into.
  • Factory Method lets subclasses decide what to create (a virtual create()); Abstract Factory creates families of related objects (for example a UI toolkit producing a matching Button and Checkbox for each platform).

Strategy

Intent: define a family of interchangeable algorithms and let the caller pick one at runtime without changing the code that uses it. Examples: sorting order, pricing rules, compression algorithms, retry policies.

Strategy vs StateThey look alike (an object delegates to a swappable helper) but differ in intent. With Strategy the client chooses the algorithm and the strategies do not know about each other. With State the object changes its own behaviour as its internal state changes, and the states themselves usually trigger the transitions.

Observer

Intent: when one object (the subject) changes, automatically notify a list of dependents (the observers) without the subject knowing who they are. This is the heart of event systems, GUI signals and publish/subscribe. Subscribe and unsubscribe observers below, then change the temperature:

Classic Observer bugs

Dangling observer: an observer is destroyed but the subject still holds its raw pointer, so the next notification calls a dead object. Fix: observers detach in their destructor (RAII), or the subject stores std::weak_ptr<Observer> and skips the expired ones.

Modifying the list while notifying: iterate over a copy, as above.

Threads: notifying from another thread needs a lock, and you should not hold it while calling observers (risk of deadlock).

State

Intent: let an object change its behaviour when its internal state changes, replacing a tangle of if (state == ...) checks scattered through every method. A turnstile is the classic example. Send events and watch it respond:

Use a state machine whenever the valid operations depend on "what mode am I in": connection handling (connecting, connected, closing), parsers, protocol handlers and device controllers. Making transitions explicit also makes illegal states unrepresentable and easy to test.

SOLID principles

Patterns are tools; SOLID explains why they work. Interviewers love it as a follow-up.

Interview cheat sheet

How do you make a Singleton thread-safe in C++?

Use a function-local static (Meyers Singleton). Since C++11 its initialization is guaranteed thread-safe and happens exactly once. Alternatives are std::call_once with an std::once_flag, or creating it before threads start. Hand-written double-checked locking is easy to get wrong. Remember the object's own methods still need locking if they mutate shared state.

What is wrong with Singleton?

It is global mutable state with a nice name: hidden dependencies, tight coupling, hard to test or mock, awkward lifetime and destruction order, and a problem for multithreading. Prefer passing a reference (dependency injection) unless a single shared instance is truly inherent.

Strategy vs State?

Both delegate behaviour to a swappable object. Strategy: the client selects an interchangeable algorithm and strategies are independent. State: the context changes its behaviour as its own state changes, and transitions are driven by the states or context.

What problems can Observer cause?

Dangling observers (destroyed but still registered), modification of the observer list during notification, unexpected notification order, cascading updates and performance issues, and thread-safety issues. Fixes: RAII detach, weak_ptr, iterate over a copy, and do not hold locks while calling out.

Why return unique_ptr from a factory?

It expresses that the caller takes sole ownership, prevents leaks, and the caller can convert it to a shared_ptr when sharing is needed. Returning a raw owning pointer is ambiguous and error-prone.

How do you replace a virtual-function Strategy in modern C++?

With a callable: store a std::function (runtime flexibility) or take a template parameter (zero overhead, compile-time choice). A lambda becomes the strategy, and no class hierarchy is needed.

What is the Open/Closed principle?

Software entities should be open to extension but closed to modification: you add new behaviour (a new strategy, a new shape type registered in a factory) without editing the existing, tested code.
