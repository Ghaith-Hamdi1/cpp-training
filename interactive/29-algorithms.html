Ranges and views (C++20)

  • A range is anything with begin() and end(). The std::ranges:: algorithms take the whole range and support projections: std::ranges::sort(people, {}, &Person::age).
  • A view is a lightweight, non-owning, lazy window (filter, transform, take, drop, reverse, iota). Pipe them with |.
  • A view does not own its data: if the container dies or reallocates, the view dangles, like string_view.
  • Ranges make pipelines readable; you do not need to know every view.

Random numbers: <random>

  • Engine plus distribution: never use rand() % n (poor quality, biased, global state). Same seed gives the same sequence (compiled: true), which is what you want in tests and simulations.
  • Compiled: 6000 rolls of the dice gave every face between 850 and 1150 times; 10,000 normal samples had a mean near 0.
  • Keep one engine per thread; engines are not thread-safe.

Cheat sheet

Answer aloud, then open.

What are C++20 ranges and views?

Ranges algorithms take a whole container (std::ranges::sort(v)) and support projections. Views are lazy, non-owning pipelines (v | views::filter(f) | views::transform(g)) that compute on demand without temporaries. Like string_view, a view dangles if its container dies.

What is the erase-remove idiom?

std::remove/remove_if only moves the elements to keep to the front and returns the new end; it cannot shrink the container. Pass that to the container's erase to actually delete the tail: v.erase(std::remove_if(...), v.end()). C++20 has std::erase_if.

Why must a comparator for sort be a strict weak ordering?

The algorithm assumes that "less" is irreflexive (comp(a, a) is false) and transitive. A comparator such as <= is true for equal elements, so sort can run past the end of the range or crash. Use <, and stable_sort when equal elements must keep their order.

Why does lower_bound need a sorted range?

It is a binary search: it compares with the middle element and discards half the range each step. That is only correct if the elements are ordered by the same comparison. On unsorted data the answer is meaningless. It is O(log n) on random-access iterators.

Why use <random> instead of rand() % n?

rand() has poor quality, global state, and the modulo skews the distribution. An engine (mt19937) produces bits and a distribution (uniform_int_distribution) shapes them; one engine per thread, seeded from random_device or a fixed value for repeatable tests.
