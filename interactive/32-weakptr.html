weak_ptr and Reference Cycles

Why shared_ptr cycles leak, how weak_ptr and lock() break them, and the three places a non-owning link belongs: parent links, caches and observers. Assumes shared_ptr.

The cycle problem

If A holds a shared_ptr to B and B holds one back to A, each keeps the other alive. When the local variables go away, both counts drop from 2 to 1, never to 0: neither object is destroyed. Compiled: both destructors never ran.

Leaks, not crashesA cycle never crashes. Memory just grows, and the destructors that would release files or sockets never run. Sanitizers with leak detection find it.

weak_ptr and lock()

A weak_ptr points at a shared object without owning it: it does not change the strong count, so it cannot keep the object alive. To use the object, ask for a temporary owner with lock().

CallMeaning
w.lock()a shared_ptr that owns the object, or an empty one
w.expired()true once every owner is gone (can change right after you ask)
w.use_count()the number of owners
w.reset()stop observing
Always lock, then testNever write if (!w.expired()) w.lock()->use(): the owner may vanish between the two calls. lock() once, test the result, use that.

Where weak_ptr belongs

Three places where a non-owning link is exactly right.

1. Parent links

A parent owns its children; a child only needs to find its parent. Make the back link weak and the tree frees itself.

2. Caches

A cache should hand out an object that is still in use, but not keep unused ones alive forever.

3. Observers

A subject keeps weak pointers to its listeners, so a listener that goes away is simply skipped and never kept alive by the subject.

What a weak_ptr keeps alive

A weak_ptr keeps the control block alive, not the object. The counts have to outlive the object so that expired() can answer.

  • With make_shared the object and the control block share one allocation, so the memory of the object is not returned until the last weak_ptr dies (the destructor still runs on time). For a huge object watched by a long-lived weak_ptr, shared_ptr<T>(new T) frees the object's memory earlier.
  • sizeof(weak_ptr) is 16 bytes, like a shared_ptr (compiled).
  • A weak pointer is for observing a shared object. For an object with a single owner use a raw pointer or reference to observe it, not a weak_ptr.

Cheat sheet

Answer aloud, then open.

How do you break a shared_ptr cycle?

Make one direction (usually the child's link to its parent) a weak_ptr. It does not count toward ownership, so the objects can be destroyed; use lock() to get a temporary shared_ptr when needed.

Why must you call lock() instead of checking expired() first?

Another thread can release the last owner between the check and the use. lock() atomically gives you an owner or an empty pointer, so test that result and use it.

What does a weak_ptr keep alive?

Only the control block (the counts), never the object. That is what lets expired() answer after the object is gone.

Why does make_shared delay freeing memory when a weak_ptr remains?

The object and the control block share one allocation. The object is destroyed on time, but the block of memory is released only when the last weak reference goes.

Name three uses of weak_ptr.

Parent back links in a tree, caches that must not keep unused entries alive, and observer lists that must not keep listeners alive.
