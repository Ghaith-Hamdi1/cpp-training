Shared data and data races

Two threads each increment a shared counter:

++counter is three CPU steps:

  1. load the value from memory into a register: r = counter
  2. add one to the register: r = r + 1
  3. store the register back to memory: counter = r

If B loads between A's load and store, one increment is lost. Play the scheduler with Step A and Step B:

Data race = undefined behaviorTwo threads access the same memory, at least one writes, no synchronization. A race condition is the wider timing-dependent logic bug.

Why it hurts: shared data has an invariant (links agree, count matches items). An update breaks it briefly, and a thread looking then sees corruption. Trouble starts when two or more pieces of data change together.

Races break invariants

A single lost increment is the easy case. The real damage comes from invariants: facts that must always hold across several variables, such as "the size matches the elements" or "the previous and next pointers agree". Any update that changes two of them takes more than one step, and in the middle the invariant is false.

TermMeaning
data racetwo threads access the same memory, at least one writes, with no synchronization: undefined behavior
race conditionthe result depends on the timing of threads; wider than a data race and possible even with atomics or locks
invarianta condition on shared data that must hold between operations
deadlockthreads wait for each other forever (next lessons)
Undefined behavior, not stale dataA data race is not just "you might read an old value". The compiler assumes there are none, and may reorder or remove code on that assumption.

Three ways to be safe

StrategyHow
1. Do not shareown data per thread (locals, thread_local), merge afterwards. Best option.
2. Share, never modifyconst data is safe to read from many threads.
3. Share and protecta mutex or an atomic.

Cheat sheet

Answer aloud, then open.

What is a data race? Is it the same as a race condition?

A data race is unsynchronised concurrent access to the same memory with at least one write: undefined behavior in C++. A race condition is the wider class of bugs where correctness depends on timing, which can exist even without a data race (two correctly locked steps that needed to be one atomic operation).

Is a function-local static initialised thread-safely?

Yes, since C++11 initialization happens exactly once even with concurrent callers ("magic statics"). That is why the Meyers Singleton is thread-safe. Using the object afterwards still needs its own synchronization.

Why is ++counter not safe on two threads?

It is three steps: load, add, store. If both threads load before either stores, one increment is lost. Use a mutex or std::atomic.

What are the three ways to share data safely?

Do not share (each thread owns its data and results are merged), share but never modify (const data), or share and protect with a mutex or an atomic.
